The backlog this page was built to track is gone. Widening the window past 08-12 for the first time shows 944 project-days holding 2,168 files between them, and 900 of those 944 cells sit at two files or fewer. Only 15 carry ten or more, and 14 of the 15 are not fragmented at all — they are the whale’s 07-20…08-02, running 0.42–1.0 GB per file against a 1 GB target. A 91 GB day should be 116 files. The single genuinely fragmented historical cell in the entire tail is whale / 08-09, 11 files for 0.9 GB. Every remaining problem on this page lives in the last seven days.

08-13 is not waiting its turn — it is being skipped. It has read exactly 167 for four consecutive snapshots, six days after sealing. The previous snapshot attributed that to scheduling_class ranking sealed work newest-first, so older days never reach the head. That explanation is now contradicted by this page’s own numbers: 08-14 (52), 08-15 (47) and 08-16 (67) are all older than the days that did run, and all three converged anyway. Pure recency ordering cannot skip 08-13 while draining its immediate neighbours. Four different projects are frozen on that one date — 00000000 35, 28f62f01 32, dcad860a 43, whale 47 — an even spread across tenants that points at something keyed on the date, not on the queue.

Where a day does start, it finishes. 08-18 has gone 979 → 798 → 501 across three snapshots, and the open partition’s smaller tenants collapsed in the same six hours (98fdd4f3 117 → 19, be87ebc1 65 → 17, d062e010 45 → 21). The mechanism works; what fails is selection. 08-17 is the counter-example still outstanding: 396 → 381, with 6297304f holding 274 of them and moving by a single file in twelve hours.

The rollup stall behind this has been fixed. Base rollup peaked at 88,618 pending units and is now ~7,600. One defect caused it: the byte estimate excluded only files entirely disjoint from a slice, then counted every remaining file whole. Maintenance files span a day, so a ten-minute slice estimated exactly what a day-wide slice did — and split_time_task, which bisects whatever “does not fit”, produced halves estimating the same, eleven times over: 87,000 units across 204 real cells, 427 per cell, 26,109 of them at the one-minute floor. Fixed by scaling each file’s contribution to the share of its own span the slice covers.

A caution about this page’s own numbers. Earlier today a companion tool reported shipbubble as 0/14 days sorted. It was wrong: pyarrow’s S3 client sends x-amz-checksum-mode, which OVH rejects, so every footer read failed — and the tool summed None as false. Re-measured, it is 9/9. The counts here come from Delta Add actions and are unaffected, but the lesson generalises: a three-valued probe must never be folded into a boolean at the summing step, or a broken measurement reads as a broken system.

On reading these numbers. Counts are active Adds in the Delta snapshot. An aws s3 ls of the same table returns 24,637 objects and suggests 350–600 files per project on 08-16 — that listing is dominated by tombstones not yet vacuumed, and the active count for those same partitions is 1–35. Worth naming because the physical listing is the easier measurement to reach for and it is wrong by an order of magnitude.
