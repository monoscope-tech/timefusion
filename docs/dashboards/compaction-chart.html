The previous crisis is fixed and a new one started on 08-24. Everything the 08-22 page called frozen has converged: the 08-13→08-18 band that was bit-identical for 58 hours now reads 25·33·17·21·73·69 files per day, 08-18 having fallen 501 → 69 and 08-17 381 → 73. The whole span 08-03 through 08-23 sits between 17 and 73 files per day. That question is closed.

What replaced it is a step, not a slope. 08-23 holds 22 files; 08-24 holds 561, 08-25 964, 08-26 736, and the open day 1,518. Three of those four are sealed and none is converging. The daily byte volume is unchanged across the boundary — 3.5 GB on 08-23 against 4.0 GB on 08-24 — so this is fragmentation, not growth. It appears in every tenant at once, from the whale (6 → 97) to 98fdd4f3 (1 → 55), and independently in otel_metrics, which steps 251 → 523 → 1,017 on exactly the same dates. A break shared by all tenants and both tables on one date is a change in the maintenance path, not tenant behaviour. My own note from 08-24 records the sealed backlog flat at 931 → 933 units over 48 minutes that day; this page is the file-count consequence of the same event. I have not identified the commit and did not try — that is the next investigation, not this chart.

The mechanism is instrumented, and the failure is memory rather than the deadline. Every ~90 seconds prod logs maintenance_hygiene_debt_unclaimed: “the most indebted hygiene cell is not being claimed”, carrying a refusal string that names what beat it — outranked_by:8100121c:2026-08-22 … 28f62f01:2026-08-26:files=294. The richest cell on the page is never claimed because an older cell always outranks it. That is the age-versus-benefit ordering defect the 08-20 and 08-22 revisions both named and neither fixed, now visible in a new form: SealedConsolidation is one lane shared across tables, so an otel_metrics cell from 08-22 outranks the 294-file otel_logs_and_spans cell from 08-26. The blocker rotates between samples (8100121c/08-22, then 00000000/08-23); what is constant is that 28f62f01/08-26 is never the winner.

And the units holding the lane are not merely slow, they are failing:

    Light optimize staging failed … table=otel_metrics: Resources exhausted:
    Additional allocation failed for SortPreservingMergeExec[0]
    Light optimize staging failed … table=otel_logs_and_spans: Not enough
    memory to continue external sort.

Both ran well inside their 900 s deadline — 763 s and 121 s — and both returned outcome=Retry. This corrects the standing assumption on the previous two revisions of this page, which attributed re-claims to deadline exhaustion. The 900 s timeout is real and separately documented, but these particular retries are an unspillable sort running out of memory, which is the SortPreservingMergeExec failure this codebase last hit on 08-09. Frequency: 5 staging failures in 90 minutes (3.3/hr) against 17 OPTIMIZE commits in 6.1 hours (2.8/hr). More sealed rewrites fail than succeed, which is precisely how a lane stays busy while file counts do not move. light_optimize_memory_brakes_total reads 263 against 108 bins committed, consistent with the same picture.

Six cells, 1,030 files, 3.75 GB to rewrite. The three sealed days together are 2,261 files over 10.4 GB — at the 512 MB sealed target that is a floor of about 21 files, so ~99% of those files are removable for the cost of rewriting ten gigabytes.

Correcting this page's own yardstick. Previous revisions measured convergence against a 1 GB target. That is wrong: .env.prod sets TIMEFUSION_OPTIMIZE_TARGET_SIZE=536870912 and the sealed/cold tier packs to 512 MB, while the warm tier for the current day uses 256 MB (the live OPTIMIZE commits carry targetSize: 268435456). The converged days bear this out at roughly 230 MB per file. The correction matters most for the whale tail below: at 0.5–0.8 GB per file those fourteen days are already above the 512 MB target, so the “debt” there is not merely low-yield, it is negative — rewriting them would increase the file count. They should be excluded from the sealed queue outright rather than ranked last.

What to do, in order. First, make the sort spill or shrink the unit — while staging fails 3.3 times an hour no ordering change can help, because nothing that gets picked finishes. Second, rank by files-removed rather than age, with a starvation floor, and make the ranking aware that the lane is shared across tables. Third, exclude partitions already above target from candidacy so the whale tail stops absorbing claims. The first is now the blocker and it is a memory fix, not a scheduling one — which is the single thing this snapshot changes about the plan.

On reading these numbers. Counts are active Adds in the Delta snapshot. An aws s3 ls of the same table returns tens of thousands of objects and suggests hundreds of files per project-day — that listing is dominated by tombstones not yet vacuumed. Worth naming because the physical listing is the easier measurement to reach for and it is wrong by an order of magnitude.

A caution about this page's own numbers. On 08-22 a companion tool reported shipbubble as 0/14 days sorted. It was wrong: pyarrow's S3 client sends x-amz-checksum-mode, which OVH rejects, so every footer read failed — and the tool summed None as false. Re-measured, it was 9/9. The counts here come from Delta Add actions and are unaffected, but the lesson generalises: a three-valued probe must never be folded into a boolean at the summing step, or a broken measurement reads as a broken system.

Commit mix, for scale. Over the last 400 commits (6.1 hours): 259 WRITE:Append (ingest flush, 42.3/hr), 71 WRITE:Overwrite (maintenance rewrite, 11.6/hr), 17 OPTIMIZE (2.8/hr), one vacuum pair. Maintenance is committing steadily — it is the sealed consolidation lane specifically that is not landing, which is why total commit volume is a poor proxy for progress here.
