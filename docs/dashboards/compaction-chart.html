Table-wide, by day — the cliff, and the first dent in it

Bytes per day are flat across the 08-24 boundary; files multiply by 23×. 08-24 is the only sealed day that has moved

Two fixes shipped tonight, and they are the same bug in two places: a sort budget written in the wrong unit. Every sort in this codebase allocates decoded Arrow, and Add.size is compressed; the ratio is 12× and the repo already knew it as estimated_decoded_bytes. Two constants divided by the wrong one.

What the failure looked like. Sealed consolidation was failing, so sealed consolidation looked broken. The full reservation dump said otherwise — the operator named in the error had consumed 4.4 MB:

    ExternalSorterMerge[0](can spill: false) consumed 3.0 GB, peak 3.0 GB,
    ExternalSorterMerge[0](can spill: false) consumed 1078.3 MB,
    SortPreservingMergeExec[0](can spill: false) consumed 4.4 MB,
    Error: Failed to allocate additional 2.1 MB … 126.2 KB remain … fair(4.1 GB)

The lane that looked broken was a victim. Two whale Repair slices — sized at 256 MB compressed, i.e. ~2.7 GB decoded each — pinned the entire 4.1 GB pool, and ExternalSorterMerge cannot spill. A 21-file sealed consolidation then failed asking for 2.1 MB. Prod logged exactly slices=4 for bytes_in=910749060, which is what the arithmetic predicts. Fixed as 93cd806 (REPAIR_SLICE_DECODED_TARGET_BYTES) and 665f95e (UNSORTED_BIN_DECODED_BUDGET_BYTES).

What moved. 08-24 fell 561 → 515 on logs and 523 → 480 on metrics — the first movement on a sealed day since the cliff formed. The whale's share of 08-24 went 97 → 60. Staging failures went 3.3–4.8/hr → 0, memory brakes 11/hr → 0, the largest unspillable merge 3.0 GB → 1.46 GB, and bins now retire 15–45 files where they retired 3–7. Hot packing on today's data is healthy: 28–45 file bins staging in 1–46 s.

What did not move, and why. 08-25 and 08-26 are unchanged. Every 900-second unit on the box is otel_metrics — slices 08-17/18/19 — finishing outcome=Running having committed nothing; their bins emit wave_bin_staging_started and never wave_bin_staged. SealedConsolidation is one lane shared across tables, so sealed logs days get nothing while metrics holds it. The fix changed the shape of this: those units used to die fast on memory (121–763 s) and free the lane between attempts; now they grind the full deadline. Same pinning, costlier per attempt.

Why the metrics bins grind is not yet answered, and three plausible answers were tested and rejected. Not a tag/footer disagreement: probing the smallest files — the ones the selector actually picks, smallest-first — returned 23/23 DECLARED, 0 errors, and the reconstructed bin (23 files, 260.8 MB) matched the staged one exactly. Not memory: zero staging failures. Not permit contention: permit_wait_ms is 0.0 s on every bin. Contributory but insufficient: metrics rows are 47 bytes against logs' 155, so a 260 MB metrics bin is 5.58 M rows / 21,786 batches at the coordinator's 256-row batch size versus logs' 1.73 M / 6,740 — a 3.2× difference cannot explain ~300×. The leading untested hypothesis is cold object-store reads: the grinding cells are 9–11 days old so the cache is cold, while the fast logs bins are today's data.

The ordering defect is real but is NOT "benefit ranking is missing". It already exists — scheduling_class computes benefit = -files/64 for the hygiene operations. The problem is what precedes it in the tuple (class, damaged, starved, hole, width, benefit, order): starved is a pure age window of 3–31 days, so 28f62f01/08-27 holding 433 files at one day old loses to 00000000/08-20 holding ~4 files at eight days old. Our own instrument prints it every 60 seconds: refusal="outranked_by:00000000:2026-08-20:28f62f01:2026-08-27:files=433". And width also precedes benefit, on the stated grounds that "every hygiene unit is day-wide" — which is false: a unit traced tonight was a 12-hour slice. No ordering change should ship without a timefusion sim backtest; the rank tuple's own comments are a graveyard of ordering regressions.

Three diagnoses were refuted before the right one, and they are recorded so they are not re-run. (1) "Give TailPass::Pack a sort-partition ladder 2→1" — the coordinator path, which is all sealed consolidation, already runs at partitions: 1; the floor of 2 applies only to the cron path. (2) "Unbounded merge fan-in from smallest-first packing" — timeline matched, numbers did not: the failing unit staged 21 files, not the 118 in the task log (input_files is candidates, not the staged bin), and its merge used 4.4 MB. (3) "Tag/footer disagreement routes sorted bins into full sorts" — refuted on the correct population, above. A fourth error was mine alone and is worth naming: an early pass here reported "0 of 6,385 files carry tags", which was an artifact — deltalake's get_add_actions(flatten=True) exposes no tags key, so .get("tags") returns None for every row. A uniform extreme across 100% of rows is the tell.

The structural debt behind all of this. 917 active files exceed 512 MB, totalling 745 GB, and Repair takes exactly one file per unit — so that is 917 whole-file sorts. A footer sample across 12 dates read 11 NONE / 1 DECLARED / 0 errors, so they genuinely carry no declared order and repair is right to target them. Whale 07-28 alone is 104 files at 1.6–1.9 GB each.
