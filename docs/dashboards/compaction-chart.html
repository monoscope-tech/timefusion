Both open questions from the last snapshot now have answers, and they point opposite ways. 08-18 IS following 08-17 down — 979 → 798 in six hours — so consolidation does converge a day once it starts. But 08-13 has not moved at all: exactly 167 files for the third snapshot running, five days after sealing, while seven younger sealed days have converged past it. And 08-17 itself has now stalled at 397 (−4% in six hours, after −55% in the preceding 26). A day that converges and then stops, next to a day that never starts, is one mechanism, not two.

The ordering diagnosis was correct and remains unapplied. scheduling_class ranks sealed work strictly newest-first, and newer sealed days keep arriving, so 08-13 never reaches the head. #199 made exactly this change for the rollup tiers; file hygiene never got it. 08-13 being byte-identical across three snapshots is as clean a confirmation as this dashboard can produce — a partition skipped by seven successors is not in the order the sweep reads.

The bigger stall found today is not here. Consolidation holds at 255 and hot packing at 89, but base rollup sits at 27,824, and the cause was a single defect in how a unit’s cost is estimated: it excluded only files entirely disjoint from a slice and then counted every remaining file whole. Maintenance files span a day, so a ten-minute slice estimated exactly what a day-wide slice did — and split_time_task, which bisects whatever “does not fit”, produced halves estimating the same, eleven times over. The real journal shows the wreckage directly: 87,000 base-rollup units across 204 real (project, date) cells, 427 per cell, with 26,109 of them at the one-minute floor — below the ten-minute mint width, so they can only be split descendants. Fixed by scaling each file’s contribution to the share of its own span the slice covers; completions went 0.17/min → ~6/min.

A caution about this page’s own numbers. Earlier today a companion tool reported shipbubble as 0/14 days sorted. It was wrong: pyarrow’s S3 client sends x-amz-checksum-mode, which OVH rejects, so every footer read failed — and the tool summed None as false. Re-measured, it is 9/9. The counts on this page come from Delta Add actions and are unaffected, but the lesson generalises: a three-valued probe must never be folded into a boolean at the summing step, or a broken measurement reads as a broken system.
